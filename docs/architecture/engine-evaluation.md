# 搜索时间与局面评估

## 搜索预算

默认按时间迭代加深：完成第 1 层后继续第 2 层，以此类推。`maxDepth = 0`
表示自动，内部 64 层是递归安全界限，并不是要求电脑算完 64 层。
每个搜索节点检查单调时钟；到期后撤销当前搜索路径，只发布最后完整一层的走法和分数。
若一层都来不及完成，返回预先验证的合法走法，评分使用根局面的静态值。

| 强度预设 | 每步时间预算 | 默认深度 |
| --- | --- | --- |
| 入门 | 300 ms | 自动 |
| 普通 | 1500 ms | 自动 |
| 较强 | 5000 ms | 自动 |

人机设置允许 100–10000 ms；高级选项允许手动限制 1–32 层，0 恢复自动。
AI 对战分别使用双方强度预设的时间预算，双方均默认自动深度，也可手动限深。
棋谱命中、唯一合法走法、无合法走法、已搜索到胜负，会提前结束。
动画与 AI 对战步间停顿不属于搜索预算。实际墙钟耗时还包括 isolate 通信、调度、初始化
以及最后节点的收尾，所以预算不是硬实时保证。

旧版默认的 3/300、5/1500、8/2000，以及早期较强档 64/5000 会迁移到新预设。
自定义参数继续保留；如果之前手动设过浅层上限，需在高级选项里选择“自动”。
设置使用 schema 4；棋谱用 `aiSearchVersion` 标识新语义，避免把新保存的手动设置再次迁移。

## 静态评分：当前代码实际计算的内容

运行时搜索使用 `lib/engine/xqlite/position.dart` 的 `XqwlPosition.evaluate()`：

```text
红方基础分 = Σ 棋子位置表[红棋类型][格点]
黑方基础分 = Σ 棋子位置表[黑棋类型][翻转后的格点]
红方局面分 = 红方基础分 − 黑方基础分 + 王安全与防守阶段分
当前走子方评分 = (红走取红方局面分，黑走取其相反数) + 3
```

`cucvlPiecePos` 已把子力价值和位置奖励合并在一起，不能再叠加一遍子力基础值。
`addPiece` / `delPiece` 增量维护 `vlWhite` 与 `vlBlack`，走棋、吃子和撤销都会更新；
叶节点评分因此只需常数时间。黑棋翻转格点后复用红棋位置表。
新增的局面项同样在 `addPiece` / `delPiece` 增量维护双方士象数量与进攻权重，
叶节点评分仍为常数时间。过河的车、马、炮增加进攻权重，过河兵提供少量权重；
士象的附加价值随敌方进攻权重变化，没有进攻子力时会降低。
敌方进攻权重较高而本方缺少士象时，给王安全负分。
这些是进攻潜力的代理值，不等于真实攻击格、将杀概率或胜率。

| 棋子 | 表中非零分值范围 | 当前含义 |
| --- | --- | --- |
| 帅/将 | 1–15 | 九宫位置偏好；不代表将帅真正的子力价值 |
| 仕/士 | 20–23 | 合法防守位置的固定偏好 |
| 相/象 | 18–23 | 合法防守位置的固定偏好 |
| 马 | 78–108 | 固定位置偏好，未检查马腿是否被堵 |
| 车 | 194–233 | 固定线路/位置偏好，未计算线路实际是否畅通 |
| 炮 | 89–101 | 固定位置偏好，未单独计算炮架质量 |
| 兵/卒 | 7–44 | 过河、接近九宫的价值；到底线价值下降 |

这是引擎内部整数单位，不是胜率，也没有采用“100 分等于一个兵”的标定。
起始对称局面基础差为 0，当前走子方静态评价为 +3。

UI 的静态分来自 `Board.staticEvaluationForRed`，使用
`lib/chess/game/game_board.dart` 中另一份相同的位置表，并共用
`PositionEvaluator` 的局面项；固定红方视角且不加先手权。
测试约束两份表和最终数值一致，防止 UI 和搜索数值漂移。

## 搜索评分与静态评分的区别

AI 评估按钮会从当前局面搜索，停用开局库。返回的是最后完成层的根节点分数，
其叶节点继续做静态搜索（未被将军时搜索吃子，被将军时搜索全部应将），
所以它可以发现眼前的交换和战术，而不是直接显示当前棋子的分值总和。
引擎返回走子方视角，BLoC 再换算成红方视角；正分红优、负分黑优。

特殊评分优先于普通位置表：将死/困毙使用 `-10000 + 搜索距离`；
超过 ±9800 视作已找到胜负；长将相关判定使用约 ±9900；
重复局面使用带搜索距离奇偶方向的 20 分和棋偏好。
根节点无合法走法一律负分，包含未被将军的困毙。唯一走法分支快速返回一步后的静态分。

## 当前不足与后续优化顺序

1. **机动性**：没有独立奖励车路、炮路、马可走格，也没有量化塞象眼、蹩马腿。
   逐叶扫描棋盘实现过一次，但固定 500 ms 开局测试的完成深度从 8/7/8 降为
   7/7/7，因此没有保留。需要增量特征或分层/懒惰评价后再试。
2. **将帅安全**：目前仅有子力权重与士象数的粗略代理值，没有围攻九宫、炮架、
   棋子实际攻击格、牵制与攻子协同分。不能将其解释成准确的王安全模型。
3. **局面阶段**：士象价值会随敌方进攻潜力变化，但其他位置表仍未按中残局插值。
4. **兵结构与交换质量**：缺少联兵、通路兵、受攻击与受保护关系的显式项。
   当前主要依赖搜索发现失子；静态交换评估可同时改善走法排序和部分剪枝。
5. **重复局面与缓存**：置换表按棋面缓存，但重复规则依赖历史路径。
   长将/长捉规则与缓存交互需要专项验收，不能把当前分值当成完整竞赛裁决。

前一轮优先解除默认浅层限制，保留位置表权重，便于区分搜索预算改善与评估调参的效果。
增加新评估项后应验收战术题、残局题、颜色翻转对称性、走棋/撤销一致性、固定时间节点吞吐量，
再做固定开局、交换红黑双方的自动对局。更深的搜索不等同于已经证明的棋力提升。

## 2026-09-28 本机基准

在同一台 macOS 机器、Flutter JIT 测试运行环境下，关闭开局库，各次搜索使用新的引擎实例：

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 基础战术命中 | 6/6 | 6/6 |
| 三个开局局面完成深度 | 8、7、8 | 8、7、8 |
| 三个开局局面总搜索节点（各 500 ms） | 约 143 万 | 约 163 万 |

节点吞吐提高约 14%。主要变化是按搜索距离复用走法列表，减少短命列表分配；
时钟由每节点读取改为每 64 个访问节点采样一次，根节点仍逐着检查。
根节点优先尝试已缓存的走法，没有缓存时选用一步静态分值最高的合法走法作为首选。
6/6 是这个小型测试集的基础战术分数，涉及无保护的车与单车将军，不能换算 Elo 或说明实战胜率。
同一时间内完成的整层深度暂未提高，因此“更强”还需扩充中盘战术题、残局题和交换先后手的固定预算对局来验证。
节点数量受 JIT 预热与机器负载影响；复测时同时看命中率、完成层数和节点数。

## 2026-09-29 评估改动与后续路线

本轮先用同一基准测量：在当前分支修改前，基础战术 6/6，三个开局各 500 ms
完成 8/7/8 层，总计约 167 万节点。增量局面项之后仍为 6/6、8/7/8 层，
总计约 164 万节点。该差距受运行环境影响，不能视作棋力提升的证据。
新增红黑翻转对称、局面项增量/全量一致、防守阶段价值和 AI 对战动画棋钟测试。

参考实现取舍：

- [Pikafish](https://github.com/official-pikafish/Pikafish) 是 UCI 原生引擎，
  使用 NNUE 网络与大规模对局测试；不能把它的棋力归结为一张手工位置表。
  项目采用 GPL-3.0，若将二进制随应用分发，须满足相应源码与许可义务。
- [ElephantEye](https://github.com/xqbase/eleeye) 描述了 UCCI、时间分配、
  带检验空着裁剪、分层评价、进攻/防守和开中残局预评价；采用 LGPL-2.1。
  当前 Dart 引擎只覆盖其中一部分，不能据此宣称达到其棋力。
- [xiangqi.com 分析棋盘](https://play.xiangqi.com/analysis/board) 可用作分析交互参考；
  页面本身不足以证明其底层引擎的具体算法。

下一阶段优先建立保存棋谱导出的困难中残局题库，以 Pikafish 的固定版本和固定
时限分析作为外部参考，记录候选着、分数、完成深度、耗时和胜负结果。
评估新特征时做相同时间预算的双向对局，而不是只比较静态分数或节点数。
若目标是明显接近专业引擎，应单独评估 Android/iOS/macOS 原生 UCI 引擎接入、
NNUE 资源体积、设备功耗与许可合规；继续堆叠 Dart 手工权重无法保证这一目标。
